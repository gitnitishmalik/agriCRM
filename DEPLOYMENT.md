# Deployment

Frontend on Vercel, backend on Render, PostgreSQL on a managed provider in
**ap-south-1 (Mumbai)**.

---

## 🔴 Read this before you put real data in it

This stack is a **staging environment**. It must hold synthetic or irreversibly
anonymised data only.

**Render has no India region.** Its closest is Singapore. Doc 03 §7 and Doc 01
§5 both mark data residency as compliance-critical — all personal data stored
and processed in ap-south-1 — and Doc 00 sells that residency to cooperative
banks and government-linked buyers. Real farmer PII on Render breaks that
position, and R11 independently forbids production PII in staging.

That is not a reason to avoid this deployment. It is a reason to be clear about
what it is: a place to demo the system, exercise the pipeline, and let people
use the screens. Production belongs on the AWS ap-south-1 topology already
described in `config/settings/production.py` and costed in Doc 14.

Generate data with `manage.py generate_synthetic_data` rather than copying a
production dump. That command exists specifically so copying is never the path
of least resistance.

## The database

You asked for PostgreSQL that can handle your data. Here is the honest shape of
that, because the answer changes by phase.

### Do not use Render's PostgreSQL

Two disqualifying problems, independent of price:

- **The free instance is deleted after 90 days.** Not archived — deleted.
- **No India region**, so it cannot ever hold production data.

### Use Neon or Supabase, in ap-south-1

Both are managed Postgres with a free tier, both support every extension this
schema needs (`pg_trgm`, `btree_gist`, `unaccent`, and PostGIS when you enable
the commented-out geometry columns), and both offer a Mumbai region.

🔴 **Confirm the region says Mumbai / ap-south-1 at project creation.** A
project cannot be moved between regions afterwards — you would have to dump,
recreate and restore. This is the one setup step where a mistake is expensive.

### What each tier actually holds

Doc 02 §7 estimates ~160 GB at three years and 10M farmers. Free tiers are
nowhere near that, and that is fine, because you do not have 10M farmers today.

| Stage | Data | Fits in |
|---|---|---|
| **Now** — Phase 0–1 staging | Geography for **two states**, ~35k FPOs, ~530 mills, people | Neon / Supabase free (0.5 GB) |
| All-India LGD geography | ~660k villages plus trigram indexes | ~250–400 MB on its own — tight on free, comfortable on the first paid tier |
| Phase 2–3 with real farmers | Farmers, land, crops, consent ledger | ~10 GB tier (Neon Launch ≈ $19/mo, Supabase Pro ≈ $25/mo) |
| Doc 02's full projection | 10M farmers, 100M messages | RDS Multi-AZ per Doc 14 — ₹28k/mo year one |

**The free tier pushes you toward the right strategy anyway.** Doc 13 §7 item 6
already says to pick your first two states — almost certainly UP and
Maharashtra given the sugar focus — because *"depth in two states beats breadth
in twenty."* Loading LGD geography for two states instead of all 36 keeps you
inside the free tier and is what the plan asked for regardless.

### Setting it up

```bash
# 1. Create the project in ap-south-1 (Mumbai). Copy the connection string.

# 2. Apply the schema. It is DDL, not Django migrations.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f agri-crm-docs/sql/schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f agri-crm-docs/sql/seed_reference.sql

# 3. Prove the triggers survived the trip. Non-negotiable.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f agri-crm-docs/sql/smoke_test.sql
# Expect 15 PASS lines. Fewer means a trigger did not apply — stop and fix it.

# 4. Django's own tables.
cd backend && DATABASE_URL="..." python manage.py migrate
```

Step 3 matters more than it looks. The compliance controls in this system are
triggers and constraints — an append-only consent ledger, suppression
outranking a fresh opt-in, `loss_reason` required on a lost opportunity. If any
of those silently failed to apply, the application will happily run without
them.

## Backend on Render

`render.yaml` at the repo root is a blueprint — point Render at the repo and it
reads it.

Set these three by hand (they are `sync: false`, so they are never committed):

| Variable | Value |
|---|---|
| `DATABASE_URL` | Your Neon/Supabase ap-south-1 connection string |
| `CORS_ALLOWED_ORIGINS` | `https://<your-project>.vercel.app` |
| `SENTRY_DSN` | Optional |

`DJANGO_SECRET_KEY` is generated by Render. `DJANGO_SETTINGS_MODULE` is already
set to `config.settings.render`.

### Two free-tier constraints that will bite

**Services sleep after 15 minutes idle and take ~50 seconds to wake.** The
first request after a quiet period will look broken to anyone you are demoing
to. Render's Starter plan (~$7/mo) removes this, and it is the single best
seven dollars in this stack.

**There is no background worker on the free tier**, so Celery runs eagerly —
inside the web request. Acceptable for a demo. **Not acceptable from Phase 4
onward**: a campaign send cannot block an HTTP request, and the dispatch-time
consent re-check (R7) needs a real worker to be meaningful. Budget a paid
worker service before you build messaging.

## Frontend on Vercel

Import the repo, set the root directory to `frontend`. `vercel.json` handles
the rest.

**Edit one line before your first deploy** — the API host in `vercel.json`:

```json
{ "source": "/api/:path*", "destination": "https://YOUR-SERVICE.onrender.com/api/:path*" }
```

That rewrite means the browser only ever sees one origin, so there is no CORS
preflight and no second code path. It is the same shape as the Vite dev proxy,
which is why local and deployed behave identically.

No environment variables are needed. `VITE_API_URL` exists for the case where
you deliberately want cross-origin calls instead of the rewrite.

## Order of operations

1. Create the database in **ap-south-1**, apply schema + seed, **run the smoke test**
2. Deploy the backend to Render, set `DATABASE_URL`, confirm `/api/v1/healthz/`
3. Put the Render URL into `frontend/vercel.json`
4. Deploy the frontend to Vercel
5. Set `CORS_ALLOWED_ORIGINS` on Render to the Vercel URL
6. Create a user: `render exec` → `python manage.py createsuperuser`

### Check it worked

```bash
curl https://YOUR-SERVICE.onrender.com/api/v1/healthz/          # {"status":"ok"}
curl https://YOUR-PROJECT.vercel.app/api/v1/healthz/            # same, through the rewrite
```

The second one is the real test: it proves the rewrite is wired, which is the
part most likely to be wrong.

## Moving to production later

Nothing here is a dead end. `config/settings/production.py` already describes
the AWS ap-south-1 target, and the application code does not change — only
settings, and the database endpoint. What you will add:

- ECS Fargate for api / worker / beat / collector, and 🔴 exactly one beat task
- RDS Multi-AZ in ap-south-1, with a tested restore
- S3 with SSE-KMS for documents, imports and exports
- Secrets Manager instead of environment variables
- Real WhatsApp and SES backends, after Meta business verification (Track P3)

The Phase 7 exit gate — load test at 3× peak, a DR drill that meets the RTO,
pen-test findings closed — is written against that topology, not this one.
